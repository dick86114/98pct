## 一、 方案目的

本规范旨在明确开发、测试、发布及运维各环节的操作标准。通过将上线验证工作前置并分散到整个交付周期，避免问题在发版日集中爆发，从而有效降低上线风险与压力，确保发布过程平稳、有序。

## 二、 角色及职责划分

| 角色          | 职责描述                                                     |
| ------------- | ------------------------------------------------------------ |
| 项目经理 (PM) | 流程发起者与总协调人。负责确认发版时间点、通知各方相关人员，不负责具体技术细节的验证。 |
| 开发人员 (RD) | 负责代码合并、提交变更说明、制定回滚方案，并配合部署工作。   |
| 测试人员 (QA) | 负责功能验收、冒烟测试执行及线上回归验证，确保质量。         |
| 产品经理 (PO) | 负责业务验收，确认本次上线的功能范围。                       |
| DBA及运维     | 负责数据备份、数据库变更执行及生产环境配置维护。             |

## 三、 基本规定与红线

1. 数据流向管控：严禁直连现网（生产）数据库进行非常规操作。仅允许将现网数据覆盖至测试环境（用于数据调试），严禁反向操作（测试数据覆盖现网）。
2. 操作授权：严禁擅自操作现网环境。所有变更操作必须获得项目经理（PM）授权，并形成操作记录。
3. 安全保障：任何变更操作前，必须制定回滚方案，并完成数据与配置的备份工作。

## 四、 发版准备阶段

本阶段旨在确保发版内容已完整验证，且具备上线条件。

### 1. 代码提交与自测 (RD)

开发完成功能开发后，合并代码至发版分支，并进行本地自测。

- 测试本次提交的功能
- 测试移动端兼容性
- 测试配置变更或数据库变更影响的关联模块
- 提交代码至发版分支
- 填写《发版申请表》

### 2. 功能测试 (QA)

QA 根据功能变更和回归需求，复用已有用例并补充变更点用例，执行功能测试。

- 编写或复用测试用例
- 确认覆盖所有变更点（包含移动端）
- 执行全量回归测试
- 测试可能受影响的关联模块
- 补充自动化回归测试脚本
- 输出物：测试报告

### 3. 产品验收 (PO)

PO 在测试环境体验核心功能，确认符合上线预期。

- 核对当次发版需求范围
- 核对核心业务流程是否正常
- 确认测试报告中记录的问题是否影响此次发版
- 核对列表、详情页的数字、状态、文案显示
- 检查有无错别字、按钮位置、报错提示是否友好
- 检查移动端相关功能体验
- 输出物：验收报告

### 4. 提交发版申请 (RD)

开发人员填写《发版申请表》，包含以下要素：

- 代码改动内容说明
- SQL 变更脚本
- 配置变更项
- 回滚方案详述

### 5. 发版评审 (PM 召集)

PM 召集开发、测试、产品及 DBA 进行发版评审会，确认以下清单：

- 测试是否通过
- PO 是否确认可以上线
- DBA 评审 SQL 脚本结果
- 回滚方案是否合理可行
- 确定发版具体时间窗口
- 同步停机/升级通知至项目组及客户

> 准备阶段核心检查清单
>
> - 代码已合并至发版分支，RD 确认自测通过。
> - 测试报告已输出，QA 确认测试通过。
> - 产品经理确认验收通过。
> - 《发版申请表》已填写完整。
> - DBA 已审核 SQL 脚本及回滚脚本，确认在“预发布环境”跑通。
> - 回退方案和步骤已确认。
> - 与客户确认停机/升级通知已发送。

## 五、 发版实施阶段

### 1. 最后检查与备份

DBA 对数据库进行备份，运维对代码包及配置进行备份。备份完成后通知 PM，正式开始发版。

- DBA 确认：数据库备份完成（附截图）
- 运维确认：代码/配置备份完成
- PM 宣布：发版正式开始

### 2. 停服

运维按计划停止相关对外服务。

### 3. 变更执行

- 数据库变更：DBA 执行 SQL 脚本，确认执行无报错。
- 代码部署：运维/开发执行代码部署，确认部署过程无误。

### 4. 启动与自检

启动服务，开发人员查看应用日志，确认进程启动正常，无 ERROR 报错信息。

- 运维/开发确认服务启动成功
- 开发确认：应用日志无异常 ERROR

> 实施阶段核心检查清单
>
> - 所有相关人员（RD、QA、DBA、PO）已在线就位。
> - 数据库备份完成（已截图留存）。
> - 代码/配置文件备份完成。
> - SQL 脚本执行无误。
> - 代码包部署成功。
> - 应用日志无异常错误信息。

## 六、 发版验证阶段

### 1. 功能验证 (QA)

QA 执行核心链路冒烟测试（限时 5-10 分钟）。

- 验证本次更新功能是否正常
- 验证核心业务流程是否通畅
- 运行自动化回归测试脚本
- 异常处理：若验证失败，开发介入排查；若评估问题严重且短时无法解决，立即启动回滚方案。
- 输出物：正式环境测试报告

### 2. 产品验收 (PO)

PO 快速确认新功能在现网的展示效果是否符合预期。

### 3. 发版结束与观察

发版完成后持续观察 15-30 分钟，确认系统状态。

- 场景一（成功）：一切正常，PM 通知客户发版结束，进行文档归档。
- 场景二（失败）：执行回滚，通知客户推迟上线，详细记录相关问题。

> 验证阶段核心检查清单
>
> - 冒烟测试通过（核心流程 5-10 分钟快速验证）。
> - 产品经理确认新功能展示正常。
> - 开发观察日志平台，确认无持续报错。
> - 正式环境测试报告已提交。
> - 完成发版结果登记并通知所有相关人员。
